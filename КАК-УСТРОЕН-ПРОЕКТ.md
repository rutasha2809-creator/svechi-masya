## 3. Устройство приложения

Одна самодостаточная HTML-страница `index.html` (~390 КБ). Ни сборки, ни зависимостей,
ни сервера. Открывается двойным кликом с диска и работает офлайн.

Внутри четыре логических слоя, склеенных в один файл:

1. **Стили и разметка** — CSS-переменные темы, четыре вкладки, шторки поверх экрана.
2. **`SEED`** — данные, извлечённые из Excel: 481 материал, 71 изделие, 21 группа
   материалов с русскими названиями. По умолчанию НЕ загружаются: приложение стартует пустым,
   пример поднимается кнопкой «Ещё → Загрузить пример из Excel».
3. **Движок расчёта** — чистые функции, никакого DOM.
4. **Синхронизация и интерфейс.**

### Модель данных

```
S = { materials: [], recipes: [], cats: [], settings: {}, log: [],
      orders: [],       // заказы: {id, d, n, items:[{rid,n,q,price}],
                        //          pack:[{mid,n,u,q,price}], tax:'none'|'fiz'|'ur'}
      taxPaid: {},      // отметки об оплате налога: {'2026-08': {d, sum}}
      accGroups: {},    // разделы справочника → 'opr' | 'ohr'

      demo: false, v: 2 }
```

**Заказ** — то, что продано клиенту. Изделия с количеством, блок упаковки (коробки,
наполнители, открытки, ленты — выбираются галочками из разделов `PACK_G`) и налог
с итоговой суммы. Упаковку клиент оплачивает, поэтому она входит и в стоимость заказа,
и в базу налога; цена подставляется закупочная, владелец правит на ту, по которой берёт.
Ставки: без налога, 4 % физлицам, 6 % юрлицам. Цены позиций записываются в момент
добавления и сами не меняются — в заказе должно остаться то, по чему продали; кнопка
«Подставить нынешние» пересчитывает их по требованию. **Заказ не списывает материалы** —
это по-прежнему делает «Выпуск». Налог за месяц собирается в ведомости, там же кнопка
«Отметить оплаченным»; если после отметки заказы месяца правили, ведомость показывает
расхождение между отмеченной и начисленной суммой.

**Настройки** (`S.settings`): `coef` — коэффициент цены, `round` — шаг округления цены,
`kwt` — тариф за кВт·ч, `low` — порог «на исходе», `base` — `'lot'` или `'avg'`,
`dep`/`opr`/`ohr` — проценты амортизации, общепроизводственных и общехозяйственных,
`legacy` — режим сверки с Excel.

**Материал**
```
{ id, g:группа, n:название, u:единица расхода, bu:единица закупки,
  pq/pp:последняя закупка (кол-во и сумма), p:цена за единицу,
  s:остаток, min:порог предупреждения, lots:[партии], x:{coef,uses} }
```

**Партия** (`lot`) — ключевая сущность склада:
```
{ id, q:осталось, q0:куплено, p:цена за единицу, d:дата,
  bq/bu:сколько и в чём куплено, sum:заплачено }
```
Цена партии фиксируется в день покупки и больше не меняется. Ничего не усредняется —
это осознанное требование владельца: материалы покупаются на маркетплейсах по разной цене.

**Изделие**
```
{ id, n, c:категория, coef:своя наценка,
  p:{параметры}, l:[строки состава], mk:[наценки], en:[электроэнергия],
  tl:[амортизация], ex:доп.расходы, xl:значение из Excel для сверки }
```

Строка состава: `{ r:номер, lb:подпись, g:группа, m:id материала, lot:id партии,
q:правило количества, cf:формат }`.

Правила количества: `const` (фикс. число), `param` (масса воска / отдушки / длина фитиля),
`pct` (процент от массы воска или гипса), `gypsumMass`, `water`.

### Логика расчёта

Себестоимость собирается построчно, как в изделии и заведено:

1. **Материалы и упаковка** — количество × цена. Цена берётся из партии «в работе»
   (самой старой непустой). Выбрать партию руками нельзя — см. раздел 24.
   **Средневзвешенная в ценах не участвует** — см. раздел 6.
2. **Электроэнергия** — мощность прибора × часы × тариф из настроек.
3. **Амортизация оборудования** — отдельной строкой на каждый предмет: воскоплав,
   весы, ложка, термометр, фен, иглы, формы. Сумма берётся из карточки предмета.
   В себестоимость входит, со склада НЕ списывается.
4. **Проценты сверху** — строками в изделии: общепроизводственные, общехозяйственные,
   расходники. Три вида базы: `k:'sum'` — от диапазона строк, `k:'prev'` — каскадом
   от предыдущей наценки, `k:'all'` — от всего выше, кроме самих наценок.
5. **Дополнительные расходы**, если заданы.

Почему построчно, а не единым процентом на всё: у восковых и гипсовых изделий
разное оборудование. В гипсовом изделии просто нет строки воскоплава — и вопрос
«какая база для амортизации» не возникает. Единый процент от прямых затрат такие
изделия завышал бы: по примеру из базы амортизация построчно даёт 12,86 ₽, а
10 % от материалов — 42,74 ₽.

**Производные величины:**

- `waxRaw = объём × 0.95` — воск вместе с отдушкой, **округляется до целых граммов**.
  До десятков округлять нельзя: так делал Excel, и 280 мл давали 270 г вместо 266,
  приписывая изделию лишние граммы. А до целых нужно — мастер отвешивает граммы,
  дробей на весах не бывает.
- `waxNet = waxRaw / (%отдушки + 100) × 100`, тоже до целых.
- `fragrMass = waxRaw − waxNet` — остатком, а не отдельным округлением. Поэтому воск
  и отдушка всегда дают в сумме ровно массу: ни потерянного, ни лишнего грамма.
  Контроль: 280 мл при 10 % → 266 г, воск 242 г, отдушка 24 г.
- масса гипса = коэффициент смеси × объём формы (СКУЛЬПТОР 1.65, жидкая керамика 1.75,
  фрипласт 1.8, акрил 1.95); вода = 25 % от гипса, она бесплатная
- Цена продажи = себестоимость × коэффициент, округление вверх до шага
  (по умолчанию ×3, до 10 ₽); у каждого изделия может быть свой коэффициент

### Единицы измерения

Базовые (расход): `г, мл, см, шт, исп.` Закупочные подставляются автоматически:
для граммов — г/кг, для миллилитров — мл/л, для сантиметров — см/м.
Пересчёт при закупке: кг→г ×1000, л→мл ×1000, м→см ×100.

## 4. Общая база (Supabase)

Таблица `public.app_state` — **одна строка на всю базу**:
```sql
id int primary key (=1), data jsonb, version bigint,
updated_at timestamptz, updated_by text
```
RLS включён, три политики (`app_state_sel` / `_ins` / `_upd`) только для роли `authenticated`.
Без входа чтение возвращает `[]`, запись затрагивает 0 строк.

**Как работает синхронизация**

- Всё состояние приложения целиком лежит в `data`.
- Сохранение локально мгновенное, выгрузка в облако с задержкой 1,2 с.
- Запись с оптимистической блокировкой: `PATCH ?id=eq.1&version=eq.<известная>`.
  Пустой ответ = кто-то сохранил раньше → полоса конфликта с выбором
  «Оставить мои» / «Взять из базы». Автослияния нет — для 2-3 человек не окупается.
- Опрос раз в 20 с запрашивает **только** `select=version,updated_at,updated_by`.
  Полные данные тянутся, лишь когда версия выросла. Это важно: состояние весит ~300 КБ,
  и полный опрос сжёг бы бесплатный трафик за пару дней.
- **Страховка:** пустая локальная копия не перезаписывает непустую общую базу.
  Показывается предупреждение с выбором.
- Без сети приложение работает на локальной копии, плашка показывает «нет связи».
- На первом экране выбор: «Войти в общую базу» или «Работать только на этом устройстве».

**Ограничения бесплатного тарифа:** проект засыпает после 7 дней без обращений
(данные целы, будится кнопкой Restore в дашборде); автоматических резервных копий нет —
владелец делает их вручную через «Ещё → Скачать базу».

## 5. Как выкатывать обновления

Рабочая папка проекта — это одновременно git-репозиторий.

1. Положить новый `index.html` в `Себестоимость\`
2. Двойной клик по **`Обновить сайт.bat`**
3. Через минуту сайт обновлён; на странице Ctrl+Shift+R, если видна старая версия

**Требования к скрипту деплоя** (проверены на практике, не упрощать):

- Удалять `.git\index.lock` и `.git\HEAD.lock` **перед** `git add`. Папка в OneDrive,
  синхронизация оставляет lock-файлы, из-за них `git add` падает, индекс остаётся пустым,
  и скрипт молча рапортует «изменений нет».
- `git push origin HEAD:main`, никогда не `git push origin main` — локальная ветка
  может называться `master`.
- Ошибка `git commit` («nothing to commit») — не повод выйти: пушить дальше,
  иначе повиснут закоммиченные, но не отправленные правки.
- Не прятать вывод git за `>nul`, печатать `git status --short`.
- Текст в .bat только латиницей: кириллица зависит от кодовой страницы.

`.gitignore` работает по принципу «запрещено всё, разрешено точечно»: выкладываются только
`index.html`, `README.md`, документы и сам .bat. Рабочий Excel и архивы остаются на компьютере.

## 6. Проверки перед отправкой новой версии

В папке `tests\` лежат автотесты. Браузер и установка библиотек не нужны —
только Node.js. Подробности в `tests\README.md`.

**Запуск: двойной клик по «Проверить приложение.bat»** в папке проекта.
Или `node tests/run-all.js`.

| Файл | Что проверяет |
|---|---|
| `syntax-test.js` | целостность index.html: разметка, синтаксис скрипта, все ключевые куски на месте, секретного ключа Supabase в файле нет |
| `test.js` | себестоимость 71 изделия против эталона `tests/эталон.json` — ловит любой незаметный сдвиг расчёта |
| `markup-test.js` | наценки `sum` / `prev` / `all`, усадка воска, отдушка без округления, масса гипса и вода, коэффициенты смесей |
| `pick-test.js` | выбор галочками: материалы, упаковка и амортизируемые предметы добавляются пачкой; амортизация считается по карточкам предметов |
| `order-test.js` | заказы и налог: ставки, итог за месяц, отметка об оплате |
| `lot-test.js` | партии: закупка в кг при расходе в г, две цены рядом, партия «в работе», выбор партии, списание выбранной |
| `avg-test.js` | средневзвешенная против примера бухгалтера (16,67 / 100,02 / 399,98), переход остатка на следующий месяц, перерасход |
| `pack-test.js` | упаковка в изделии: входит в себестоимость, но не в базу процентов; задвоение с заказом |
| `auth-test.js` | восстановление пароля (разбор ссылки, запрос письма, смена) и копии базы |
| `sync-test.js` | синхронизация: неотправленные правки не затираются общей базой |
| `chain-test.js` | вся цепочка на пустом приложении, все экраны строятся без ошибок |

**Как это работает.** `tests/harness.js` достаёт из `index.html` скрипт
приложения, обрезает его по метке `/* --- старт --- */` и выполняет остаток
в Node с заглушками вместо браузера. Поэтому:

> **Метку `/* --- старт --- */` перед строкой `S=load()` трогать нельзя.**
> Без неё тесты не запустятся. Они об этом скажут прямым текстом, но лучше
> просто оставить её на месте.

**Эталон.** «Совпало 63» больше не мерило: с 30.08.2026 расчёт разошёлся с Excel
намеренно. Вместо этого `test.js` сверяет себестоимость с `tests/эталон.json` — снимком
с исправной версии. Если расчёт изменили осознанно и цифры верны:

    node tests/test.js --обновить

и закоммитить `эталон.json` вместе с `index.html`. Расхождение с Excel печатается
справочно и ошибкой не считается.

Набор проверен на нарочно испорченных копиях: ловит возврат округления массы воска,
округление доли отдушки, сломанные галочки (перестают копить выбор, берут только первую
позицию, теряют привязку к предмету), сбитую базу процента и любую синтаксическую опечатку.

Если тест ругается, а правило расчёта действительно поменялось — правится
тест, рядом с каждой цифрой в нём написано, откуда она взялась. Подгонять
ожидаемое значение, не разобравшись, нельзя: тест перестанет ловить настоящую
поломку.

## 7. Принятые решения и почему

- **Интерфейс не повторяет структуру Excel.** Первая версия повторяла — владелец сказал
  «слишком сложно, похоже на эксель». Пустые строки состава прячутся, группировка по смыслу
  (материалы / упаковка / прочие расходы), правка цены в один тап оттуда, где увидел проблему.
- **Приложение стартует пустым** — чтобы мастер прошёл всю цепочку с нуля и было видно,
  где интерфейс не объясняет себя сам.
- **Партии вместо средней цены** — материалы покупаются на маркетплейсах по разной цене,
  владельцу нужна цена конкретной покупки, а не абстрактная средняя.
- **Репозиторий публичный** — осознанно, ради бесплатного GitHub Pages. Владелец предупреждён,
  что закупочные цены в коде видны всем.
- **Никаких кодов и идентификаторов в интерфейсе** — только выпадающие списки по-русски.
- **Слово «упаковка» — только про коробки и тишью.** Для размера закупки использовать
  «Купили» / «Заплатили»: в этой предметной области «упаковка» занята.

- электроэнергия считается по единой мощности на все предметы — 12 кВт не ошибка.

## 10. Что изменилось 30.08.2026

Схема расчёта осталась прежней — построчной. Изменились три вещи:

1. **Отдушка считается без округления** (см. раздел 3). Это осознанный разрыв с Excel:
   64 изделия из 71 остаются в пределах 3 % от цифры файла, остальные — известные
   ошибки самого Excel.
2. **Выбор галочками.** «+ добавить материал», «+ добавить упаковку» и «+ амортизация»
   открывают список с галочками: отмечаете сколько нужно позиций — воскоплав, весы,
   термометр — и добавляете одной кнопкой. Есть «отметить все показанные» и «очистить».
   Если отметить одну позицию, сразу открывается её карточка, как раньше.
3. **Тип изделия при создании.** Раньше любое новое изделие получало восковые
   параметры, и у гипсового подноса просили заполнить объём формы для воска,
   отдушку и длину фитиля. Теперь при создании выбирается тип:
   **восковое** (объём формы, отдушка, фитиль, формула усадки),
   **гипсовое** (объём формы для гипса; сразу заводятся две строки — гипс и вода,
   масса гипса и вода считаются сами) или **другое** (без параметров).
   Коэффициент смеси правится в карточке материала — поле появляется у материалов
   из раздела гипса; там же подсказка про 1,65 / 1,75 / 1,8 / 1,95.
4. **Средневзвешенная убрана из цен** (31.08.2026). Себестоимость всегда по цене партии.
   Из карточки изделия убран блок с двумя цифрами и разницей, из карточки материала —
   вторая цифра, из «Ещё» — переключатель «Себестоимость считать». Ведомость по
   средневзвешенной осталась отчётом.
5. **Подписи про партии.** В карточке материала, когда цена партии «в работе» и
   средневзвешенная расходятся, написано почему: одна — цена расходуемой сейчас
   закупки, другая — средняя по всем закупкам месяца, и списания на неё не влияют.
   В режиме средневзвешенной убрана фраза про выбор партии — там он ни на что не влияет.

**Тупик, в который я заходила и из которого вернулась.** В течение дня была попытка
заменить построчную амортизацию единым процентом от прямых затрат (10 % амортизация,
10 % общепроизводственные, 4 % общехозяйственные). Это оказалось неверно: построчная
амортизация даёт около 12 ₽ на изделие, а 10 % от материалов — около 43 ₽, втрое
больше, и гипсовым изделиям приписывался воскоплав, которого там нет. Схема откачена.
Если кто-то соберётся вернуться к этой идее — сначала прочитайте этот абзац.

**Открытые вопросы:**

- Вода и электроэнергия как 2 % от прямых затрат — владелец предлагала, не сделано.
- Подсказка «хватит на N штук» считает по всему складу материала, а не по выбранной
  в изделии партии. Зафиксировано в `tests/lot-test.js` как нынешнее поведение.

## 11. Заказы и налог (31.08.2026)

Появилась пятая вкладка — **«Заказы»**. Заказ собирается из изделий галочками,
у каждой позиции своё количество и цена. Отдельным блоком — упаковка заказа:
коробки, наполнители, открытки и ленты, тоже галочками, списком только из разделов
упаковки. Упаковку клиент оплачивает, поэтому она входит в стоимость заказа и в налог;
цена подставляется закупочная и правится руками. Налог выбирается из списка: без налога,
4 % физлицам, 6 % юрлицам — и считается от итоговой стоимости заказа.

Решения, которые стоит понимать:

- **Цены позиций фиксируются при добавлении.** Изделие потом подорожает, а в заказе
  останется цена, по которой продали. Пересчитать можно вручную — ссылка
  «Подставить нынешние» в карточке заказа.
- **Заказ не списывает материалы.** Списание осталось во вкладке «Выпуск», это
  отдельное действие. Если понадобится связать одно с другим — это новая работа.
- **Налог отмечается оплаченным за месяц целиком**, одной кнопкой в ведомости:
  так его и платят. Записывается дата и сумма на момент отметки. Если после этого
  заказы месяца правили, ведомость покажет расхождение и предложит переставить отметку.

## 12. Общепроизводственные и общехозяйственные (31.08.2026)

Две накопительные позиции в ведомости — как счета, с сальдо.

**Пополнение** — закупки материалов из разделов справочника, отмеченных
соответственно. Отметка ставится в «Ещё → Разделы справочника» выпадающим списком:
материалам изделий / общепроизводственным / общехозяйственным. Перчатки, салфетки,
скатерти — общепроизводственные; реклама, промо, обучение — общехозяйственные.
Закупки из отмеченных разделов не идут в состав изделий.

**Списание** — проценты, начисленные на изделия при выпуске. Какая строка наценки
к какой статье относится, приложение определяет по названию (`mkAccGuess`):
«общепроизводственные», «расходники», «разное» → ОПР; «общехозяйственные», «промо»,
«маркетинг», «реклама», «обучение» → ОХР. В карточке строки наценки это можно
переопределить вручную (`mk.acc`), в том числе выбрать «никуда — просто наценка».

**Сальдо копится:** остаток на конец месяца переходит на начало следующего, как у
материалов. Плюс означает, что потратили больше, чем разнесли по изделиям; минус —
наоборот.

Каждый выпуск записывает в журнал `acc:{opr,ohr}` — сколько начислено. Ведомость берёт
цифры оттуда, а не пересчитывает старые выпуски по нынешним процентам. Выпуски,
сделанные до появления этой ведомости, разбивки не имеют — ведомость честно пишет,
сколько таких записей.

**ИТОГО в ведомости** — в двух местах: строка под таблицей материалов (остаток на
начало, приход, списание, остаток на конец — в деньгах) и общая сводка внизу, где
собраны материалы, обе накладные статьи, выручка по заказам и налог.

## 13. Отмена записи в журнале (31.08.2026)

Ошиблись при вводе — запись в истории («Выпуск» → «История: закупки и выпуски»)
можно удалить и завести заново. Удаление не просто вычёркивает строку, а откатывает
то, что она сделала со складом:

- **выпуск** возвращает материалы — в ту партию, из которой брали, если в строке
  состава она была выбрана; иначе в партию «в работе»;
- **закупка** удаляет свою партию и уменьшает остаток.

Закупку, из которой уже списывали, удалить нельзя: остатки разошлись бы. Приложение
объясняет почему и предлагает сначала отменить выпуски. Записи, сделанные до появления
разбивки по расходу (`use`), удаляются, но склад при этом не трогают — об этом тоже
написано в диалоге.

У каждой записи журнала есть ключ `g`; у старых записей он проставляется при первом
показе. Закупка теперь запоминает `lot` — id созданной партии, иначе её нечем было бы
найти при удалении.

**Попутно исправлена ошибка:** при удалении последней партии остаток не обнулялся.
`stockOf()` при пустом списке партий возвращается к старому `m.s`, и количество
«воскресало». Теперь `lotDel()` и отмена закупки обнуляют `m.s` явно.

## 14. Вкладки «Выпуск» больше нет (31.08.2026)

Материалы уходят со склада только через заказ. Причина: заказ и выпуск дублировали
друг друга — продали три свечи и вводили это дважды, сначала во «Выпуске» ради
списания, потом в «Заказах» ради налога.

**Как теперь.** В карточке заказа кнопка «Списать материалы со склада»: проходит по
всем изделиям заказа (по их составу × количество) и по упаковке заказа, списывает всё
разом и пишет **одну** запись в журнал. Пока кнопку не нажали — склад не тронут; на
вкладке «Заказы» висит предупреждение, сколько заказов ещё без списания. Повторно
списать нельзя, отменить — ссылкой «отменить списание» в заказе или из журнала.

**Галочка «не в заказ — для своих целей»** (`o.own`): витрина, образцы, подарки, задел
впрок. Материалы списываются так же, но выручки и налога нет — `orderSum()` для таких
заказов возвращает 0, и в итог месяца они не попадают. В карточке вместо выручки
показывается себестоимость, поле выбора налога скрыто.

**Куда что переехало:**

- история закупок и списаний — вниз вкладки «Склад», там же отмена ошибочных записей;
- `doMake()`, `mkCheck()`, `renderMake()` удалены; вместо них `shipDo()` (само списание),
  `shipUsage()` / `shipCheck()` (что уйдёт и хватает ли), `renderLog()` (журнал),
  `makeBatch(r,n)` — списать партию одного изделия, используется тестами.

Вкладок стало четыре: Изделия, Склад, Заказы, Ещё.

## 15. Две ошибки от 31.08.2026 и как их не повторить

**Выбор партии «слетал».** Выпадающий список в строке состава менял только черновик
изделия (`D`), а сохранение шло через отдельную кнопку. Мастер выбирал партию, уходил,
не нажав «Сохранить», — и выбор пропадал. Теперь список зовёт `pickLot(row, value)`,
которая пишет выбор сразу в `S.recipes` и сохраняет. Тест ловит и подмену функции,
и возврат старого `onchange` прямо в разметке.

**Галочки сломали фильтры на «Складе».** Класс `.ck` в приложении уже был занят —
это `<label class="ck">` у фильтров «только те, что в рецептах» и «на исходе».
Новый квадратик-галочка для списков выбора получил то же имя, и лейблы фильтров
превратились в пустые квадраты без текста. Свой класс теперь `.ckb`.

**Вывод на будущее:** перед тем как заводить новый класс в CSS, проверьте
`grep -n "\.имя{" index.html` — файл один на всё приложение, имена стилей общие.

### 16. Текст подсказки о налоге (31.08.2026)

В карточке заказа под выбором ставки серая подсказка раньше писала
«Налог считается от стоимости заказа вместе с упаковкой: …». По просьбе
владельца упоминание упаковки убрано, осталось:
«Налог считается от итоговой стоимости заказа: сумма × ставка = налог».

Сам расчёт не менялся: база налога — это `orderSum(o)` = позиции + упаковка.
Строка живёт в `orderView()`, в тернарнике по `o.own`.

Тогда же в заказе поправлены ещё две подсказки:
- под списком изделий: «Цена товара корректируется (подставляется) на момент
  реализации» (ссылка «Подставить нынешние» осталась);
- под блоком упаковки: фраза «Упаковка входит в стоимость заказа, значит и в
  налог» убрана совсем, осталось только про закупочную цену.

Правило от владельца (31.08.2026): любые пояснительные подсказки для
пользователя внутри приложения — только по согласованию формулировки. Не
сочинять их самостоятельно. Под блоком упаковки в заказе подсказок нет вообще.

### 17. Упаковка в заказе не прибавляется к цене (31.08.2026)

Стоимость упаковки заложена в себестоимость изделия процентом от основных
затрат. Значит, прибавлять коробку ещё и к цене заказа нельзя — это задвоение.

Как теперь:
- `orderSum(o)` = только изделия (`orderItemsSum`). Налог и выручка месяца —
  от неё же;
- блок «Упаковка заказа» в карточке остался: коробки, ленты, открытки
  выбираются галочками и списываются со склада при оформлении заказа;
- у позиций упаковки больше нет поля цены — её никто не редактирует,
  функция `ordPackPrice` удалена, `ordRefreshPrices` упаковку не трогает;
- `orderPackSum(o)` теперь считает закупочную стоимость упаковки (по
  `matPrice`), а не выручку; в карточке эта сумма не показывается.

Открытый вопрос: `orderCost(o)` по-прежнему прибавляет упаковку к
себестоимости заказа поверх процента, заложенного в изделии. Нужно решение
владельца.

Дополнение к п. 17: упаковка убрана и из себестоимости заказа. Её стоимость
сидит в общепроизводственных затратах, поэтому `orderCost(o)` считает только
изделия, и `shipDo` больше не прибавляет отдельные материалы строк к сумме
записи в журнале. Со склада упаковка при этом списывается как обычно.
Открытых вопросов по упаковке не осталось.

### 18. Упаковки в изделии больше нет (31.08.2026)

Правило владельца: коробки, бумага, открытки, ленты в состав изделия не входят.
Их стоимость заложена в наценку вместе с общепроизводственными расходами, а сама
упаковка выбирается один раз на весь заказ и там же списывается со склада.

Что сделано в коде:
- `addLine(k)` теперь всегда открывает только материалы и передаёт
  `groups: groupKeys().filter(g=>!PACK_G.has(g))` — разделы упаковки (box, pack,
  label, ribbon) в списке не показываются;
- в `blockHtml` кнопка «добавить» осталась только у блока материалов
  (`addable = k==='mat'`); у блока упаковки кнопок нет вовсе, у блока «прочее» —
  прежние три (электроэнергия, амортизация, процент сверху).

Блок «Упаковка» в карточке изделия НЕ убран: у изделий, заведённых раньше, там
могут остаться строки — их видно и можно удалить вручную. Такие строки
списываются по составу, и если ту же коробку добавить ещё и в заказ, она уйдёт
со склада дважды. Проверить старые изделия и вычистить эти строки.

### 20. Трёхуровневая схема себестоимости (31.08.2026, после консультации с бухгалтером)

Себестоимость изделия теперь складывается строго из трёх уровней:

1. Прямые переменные — материалы по составу, поштучно;
2. Прямые постоянные — амортизация по позициям (карточки предметов) и
   электроэнергия;
3. Косвенные — две ОБЩИЕ строки: общепроизводственные 10 % и
   общехозяйственные 2 % от суммы уровней 1 и 2.

Что изменилось в коде:
- `DEF_SET` получил `opr:10, ohr:2` — ставки в процентах, общие для всего
  приложения, редактируются в «Ещё → Настройки»;
- `accPct(kind)` отдаёт ставку с подстраховкой значением по умолчанию;
- `calc()` после материалов, энергии и амортизации запоминает `прямые` и
  добавляет две строки `det` с признаком `acc:'opr'|'ohr'`; возвращает
  `{cost, det, d, прямые}`;
- собственные процентные строки изделия (`r.mk`) в расчёте БОЛЬШЕ НЕ
  участвуют. Данные не удаляются, но не считаются — иначе у перенесённых из
  Excel изделий всё задвоилось бы. Кнопка «+ процент сверху», карточка
  «Процент сверху», `k_set`, `mkAccGuess`, `mkAccOf`, `setMkAcc` удалены;
- `shipDo` берёт начисления ОПР/ОХР прямо из этих двух строк
  (`y.k==='k' && y.acc`) — в ведомости они списываются общей суммой с каждого
  изделия;
- упаковка вернулась в `orderCost` и в сумму записи журнала: она относится к
  прямым постоянным расходам заказа, а НЕ к ОПР. К цене заказа и к базе налога
  по-прежнему не прибавляется.

Разделам справочника «Упаковка», «Наклейки и открытки», «Ленты» признак
общепроизводственных ставить НЕ надо — это прямые расходы.

Эталон пересчитан (`node tests/test.js --обновить`). Сдвиг по 71 изделию из
файла-образца: в среднем −0,1 %, крайние значения от −7,4 % до +10,9 % —
у изделий, где в Excel была одна наценка 10 %, теперь добавились 2 % ОХР, а у
гипсовых, где наценка была выше, стало меньше.

Проверено нарочными поломками: каскад ОХР от суммы с ОПР, амортизация выпала
из базы, выпуск перестал писать разбивку, ставка ОХР подменена на 4 % — все
четыре ловятся.


### 21. Упаковка, восстановление пароля и копии базы (30.08.2026)

**Пустой блок «Упаковка» убран из карточки изделия.** Он оставался виден у изделий,
где строки упаковки были заведены, но пустые: строки уходили в «свободные слоты»,
и убрать блок с экрана было нечем. Теперь `recipeView()` вовсе не рисует блок `pack`,
если в нём нет ни одной заполненной строки:
`['mat','pack','other'].filter(k=>k!=='pack'||buck.pack.length)`.

У старых изделий с настоящей строкой упаковки блок остаётся, и в нём появилась кнопка
**«Удалить все строки упаковки»** → `delPackLines()`: чистит `D.l` по группе строки
(а если группы нет — по группе материала), пишет результат сразу в `S.recipes` и
сохраняет, чтобы правка не потерялась без нажатия «Сохранить». После этого блок
исчезает сам. Задача «проверить старые изделия и вычистить эти строки» из п. 18 закрыта:
теперь это делается из интерфейса.

**Восстановление пароля.** На экране входа появилась ссылка «Забыли пароль?».

- `gateForgot()` / `doGateForgot()` — POST `/auth/v1/recover?redirect_to=<адрес страницы>`;
- ссылка из письма приходит с меткой в адресе: `#access_token=…&type=recovery`.
  `recoveryLink()` разбирает её **вручную**, без `URLSearchParams` — этого объекта нет
  в песочнице тестов, и на старых телефонных браузерах он тоже не гарантирован;
- при старте, ДО обычного входа, `recoveryLink()` проверяется первым: с токеном
  открывается `gateNewPass()`, с ошибкой (`error_description` — обычно протухшая
  ссылка) — `gateLinkBad()` с предложением запросить письмо заново;
- `doNewPass()` — PUT `/auth/v1/user` с заголовком `Authorization: Bearer <токен из письма>`,
  тело `{password}`. Требует не меньше шести знаков и совпадения двух полей.
  После успеха адрес чистится (`clearHash()`), человек возвращается на экран входа.

Работает только на сайте: ссылка из письма ведёт на GitHub Pages, с диска (`file://`)
восстановление невозможно. В Supabase нужно один раз прописать адрес возврата —
см. `Настройка-Supabase.md`.

**Резервные копии в общей базе.** Отдельная таблица `public.app_backups`
(`id, made_at, made_by, version, data jsonb`), RLS, три политики для `authenticated`.
SQL для создания — в `Настройка-Supabase.md`, там же настройка адреса возврата.

- `bkAuto()` — раз в сутки при первом открытии, день последней копии помнится в
  `localStorage` (`masya_bk_day_v1`). Пустое состояние не сохраняется, чтобы не
  затирать историю пустышкой;
- `bkMake()` кладёт снимок, `bkPrune()` удаляет всё старше последних `BK_KEEP=14`;
- `bkList()` тянет **только** `id, made_at, made_by, version` — без `data`.
  Это принципиально: состояние весит ~300 КБ, и список с данными сжёг бы
  бесплатный трафик, как когда-то полный опрос версии (см. раздел 4).
  В `auth-test.js` есть проверка, что `select` в `bkList()` не содержит `data`;

### 24. Выбор партии в строке состава убран навсегда (30.08.2026)

Требование владельца: **списка закупок в строке состава изделия быть не должно.**
Цена берётся сама, руками партию не выбирают. Список всплывал снова и снова, каждый
раз воспринимался как ошибка — поэтому он удалён вместе со всей механикой выбора,
а не спрятан.

Как теперь:

- `matPrice(m)` — один аргумент, цена всегда от `activeLot(m)`, то есть от самой
  старой непустой закупки;
- `calc()` зовёт `matPrice(m)` и поля `l.lot` не читает;
- `priceBox()` рисует одну плашку с ценой и строкой «Закупка в работе: … .
  Закупки расходуются по очереди, от самой старой». Ни `<select>`, ни ссылки
  «взять из другой закупки» больше нет;
- `pickLot()`, `toggleLot()` и переменная `lotOpen` удалены;
- `shipUsage()` больше не собирает словарь партий, `consume()` списывает по очереди;
- отмена выпуска возвращает материал в партию «в работе» (`restoreStock` без третьего
  аргумента);
- поле `l.lot` у старых изделий в данных может остаться — оно **инертно**, ни на цену,
  ни на списание не влияет. Специально не чистим: чистка потянула бы за собой полную
  перезапись общей базы.

Тексты в двух местах поправлены следом: в карточке изделия «Цена материала берётся
из той закупки, что сейчас «в работе»», в карточке материала — «Расходуется по
очереди — сначала та, что «в работе», потом следующая по дате».

вернётся: нет `pickLot(`, нет `toggleLot(`, у `matPrice` нет параметра `lotId`,

строки состава не содержит выпадающего списка и что старое поле `l.lot` в данных
на цену не влияет. **Не ослаблять эти проверки.** Если когда-нибудь понадобится
вернуть выбор партии — сначала спросить владельца, потому что это уже отменяли.


### 25. Удалённое изделие возвращалось после обновления (30.08.2026)

Владелец завела тестовое изделие, удалила его, обновила страницу — изделие вернулось.

**Причина.** Правка ложится в браузер мгновенно, а в общую базу уходит через 1,2 с
(`cloudSchedule`). Если вкладку закрыли или обновили раньше, удаление осталось
только на устройстве. А запуск приложения делал `cloudPull` и **безусловно**
подставлял то, что лежит в базе, — вместе с только что удалённым изделием.
То же самое случилось бы с любой правкой, не только с удалением.

**Что сделано.**

- Появилась память о неотправленном: `syncMark(dirty, ver)` / `syncState()`,
  ключ `masya_sync_v1` в localStorage. `cloudSchedule()` ставит признак **до**
  задержки, успешная запись в базу его снимает и запоминает номер версии;
- стартовая синхронизация вынесена в `cloudBoot()` — раньше она жила прямо
  в стартовом блоке и её нельзя было проверить тестом. Логика теперь такая:
  неотправленное есть и в базе та же версия, что мы помним → **досылаем своё**;
  неотправленное есть, а версия в базе выросла → полоса выбора («Оставить мои» /
  «Взять из базы»), молча не затирается ничего; неотправленного нет → спокойно
  берём версию из базы, как раньше;
- `cloudFlush()` — отправить немедленно. Зовётся из `delRecipe()` и по событиям
  `pagehide`, `beforeunload` и уходу вкладки в фон, чтобы правка не осталась
  висеть в таймере;
- `cloudFirstSync()` и подтягивание чужих правок тоже проставляют `syncMark`.

**Тест `sync-test.js`** воспроизводит ровно этот случай: локально пусто, в облаке
лежит удалённое изделие, признак «неотправленное» стоит — после `cloudBoot()`
изделие не должно вернуться. Плюс случай, когда базу за это время правил кто-то
ещё (ожидается полоса выбора и никаких молчаливых перезаписей), и обычный запуск
без неотправленного.

В `tests/harness.js` для этого открыты наружу `CL`, `MODE` и `AU` — они объявлены
через `let` и снаружи песочницы иначе не видны.


### 26. Упаковка вернулась в изделие (30.08.2026)

Решение владельца отменяет пункт 18: **упаковку снова заводят в карточке изделия.**
В блоке «Упаковка» появилась своя кнопка «+ добавить упаковку», список в ней —
только разделы упаковки (коробки, наполнители, наклейки, ленты), а в списке
материалов их по-прежнему нет. Строка помечается подписью «упаковка».

**Главное в расчёте: упаковка входит в себестоимость, но НЕ входит в базу
процентов.** Стоимость упаковки уже сидит в общепроизводственных расходах,
поэтому начислять на неё сверху 10 % ОПР и 2 % ОХР — задвоение. В `calc()`
строки из `PACK_G` копятся в отдельную сумму `упаковка`, и база считается как
`прямые = total - упаковка`. Функция возвращает обе величины.

Пример из теста: воск 100 ₽ + коробка 50 ₽ → проценты берутся со 100 ₽
(10 ₽ и 2 ₽), итог 162 ₽, а не 168 ₽.

**Задвоение с заказом.** Упаковку можно завести и в изделии, и в блоке
«Упаковка заказа» — владелец попросила оставить оба места. Тогда одна и та же
коробка ушла бы со склада дважды. Приложение это ловит: `packDouble(o)` сверяет
материалы упаковки заказа с составом его изделий; совпадения показываются
красной плашкой в карточке заказа и повторяются в диалоге списания. Само
списание не блокируется — решает человек.

**Эталон пересчитан.** Сдвиг по 71 изделию из файла-образца: в среднем −1,9 %,
крайнее −4,6 % (ПАУК); вверх не сдвинулось ни одно. Это ровно те проценты,
которые раньше начислялись на упаковку.

Блок «Упаковка» снова показывается всегда — в нём есть кнопка. Кнопка
«Удалить все строки упаковки» и функция `delPackLines()` из пункта 21 удалены:
строки теперь нужны, а лишнюю можно убрать по одной, как любую другую.

**Ставка ОПР осталась 10 %.** Если она задавалась с расчётом на упаковку,
её стоит пересмотреть — это делается в «Ещё → Настройки», в коде ничего
менять не надо.

### 29. ОПР и ОХР переехали в саму ведомость (14.09.2026)

Пункт 28 оказался неверным решением: объединять статьи в одну строку не нужно,
и отдельная карточка под таблицей только дублировала отчёт. Владелец попросила
сделать наоборот.

**Как теперь.** Карточки **«Расходы общей суммой» больше нет** — функция `accHtml()`
удалена. Общепроизводственные и общехозяйственные стоят **двумя строками в теле
таблицы ведомости**, после материалов и перед итоговой строкой, в тех же денежных
колонках: на начало, приход, списание, на конец. Колонки количества и средней цены
у них пустые — у денег нет штук.

**Материалы отмеченных разделов поштучно не показываются.** Перчатки, салфетки,
промо-материалы больше не висят в ведомости отдельными позициями: `avgView()`
пропускает материалы, у которых `groupAcc(m.g)` что-то вернул, и вся их сумма
сидит в двух собранных строках. Итоговая строка называется просто **«ИТОГО»** и
складывает материалы вместе с обеими статьями (`tot` + `accBoth`).

`tot` — по-прежнему только материалы: он уходит в плитки наверху страницы и в
сводку «ИТОГО за месяц», где косвенные расходы прибавляются своей строкой.
Если бы `tot` включал их, в сводке они посчитались бы дважды.

- `accRows(ym)` — обе статьи с их цифрами, `accTableRows(ym)` — готовые строки
  таблицы, `accAny(ym)` — были ли движения (таблица рисуется и тогда, когда
  движений по материалам нет, а по статьям есть);
- предупреждения «ни один раздел не отмечен» и «списаний без разбивки» переехали
  из удалённой карточки под таблицу;
- `accLedger`, `accAt`, `accNoBreak` не менялись;
- `accBoth()` остался — на нём держится сводка «ИТОГО за месяц», где обе статьи
  по-прежнему идут двумя строками «Косвенные расходы: пополнение» и
  «Косвенные расходы: списание».

Проверки в `acc-test.js` переписаны: `accHtml` в приложении быть не должно,
в ведомости должны стоять обе строки и не должно быть общей строки на две статьи.
